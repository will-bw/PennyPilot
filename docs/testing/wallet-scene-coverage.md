# 微信与支付宝场景排查和验证（v0.5.6）

日期：2026-10-24，北京时间。本轮继续完成场景代码与自动化验证；用户选择暂不继续手机操作，因此没有进行新版本的设备覆盖安装或其他交易验收。

## 实际设备样本

设备为 RMX3888 / Android 16，微信 8.0.78；只读查询到支付宝版本为 12.12.30.8000，没有据此宣称支付宝页面已适配实测。

用户自行发出的 3 元红包，在会话内仅显示红包卡片；只读打开后，实际详情入口为 `com.tencent.mm.plugin.luckymoney.ui.LuckyMoneyNewDetailUI`，页面显示“红包金额3.00元，等待对方领取”，底部注明未领取将于 24 小时后发起退款。系统 Activity 记录确认了 `LuckyMoneyNewPrepareUI`、`UIPageFragmentActivity`、`LuckyMoneyNewReceiveUI`、`LuckyMoneyBeforeDetailUI` 与详情页的切换。该页未向现有服务提供可读文字。

这份样本证明了发送详情的入口、文字和布局；没有证明 OCR 在修复包上的实际输出，也没有验证领取结果、退款、收款码或支付宝页面。回归中的付款结果、领取结果及其他钱包页面为明确标记的合成样本。真实姓名、聊天、截图均不加入仓库。

## 已补齐的场景逻辑

| 场景 | 触发和识别 | 金额、方向与用途 | 验证层级 |
| --- | --- | --- | --- |
| 微信红包发出 | 可读发送成功结果；新准备流程之后的已核验付款截图；已核验流程中的发送详情 | 本人支出；等待对方领取不否定本人付款；用途保持未知待确认 | 详情布局有设备样本；本地 OCR 到数据库为合成回归 |
| 微信红包领取 | 可读“已领取／已存入零钱”；空节点路径要求在指定红包领取窗口观察到用户点“开”，随后识别本人已到账区域 | 只取本人领取金额；群总额和其他成员金额排除；用途保持未知 | 语义、截图与点击事件到数据库回归；实际点击事件是否含按钮文字待设备核验 |
| 微信红包退还 | 明确已退还／退回完成的通知或只读结果 | 资金转入，与收到新红包分开；不把“将于24小时后发起退款”当成已经退款 | 正反例与服务到数据库回归 |
| 微信／支付宝退款 | 通知、完成结果、含本次退款单号及实际到账时间的近期详情 | 本次退款优先；原支付金额和累计退款金额不当本次金额；处理中、已受理、预计到账拒绝 | 解析、跨来源去重、分次退款、时间和持久化回归 |
| 微信收款码 | 收款助手等可信标题通知，或明确单笔收款完成结果 | 收入资金方向；排除今日／累计收款，收款码设置金额不算到账；用途待核对 | 通知、页面及入库回归 |
| 支付宝收款 | 可信通知、收款完成结果；带收支类型、交易时间、交易单号的近期详情 | 中性“交易成功”不默认支出；取付款方作为交易对方；带正号金额须有独立收入依据 | 解析、详情及服务到数据库回归 |
| 支付宝付款 | 可信通知、付款完成结果；有独立支出依据的近期详情 | 实付与优惠、余额区分；负号凭证只在明确支出详情内解析并保留原文 | 解析、详情及服务到数据库回归 |

## 共性修复

- **退款身份**：自身退款单号使用 `wechat:refund`／`alipay:refund`，商户退款号使用独立 `merchant_refund` 命名空间。原支付号只保留在字段依据中，不作为退款的唯一身份。同笔通知与页面合并，同原订单的两次相同金额退款保留两笔。
- **迟到身份**：无单号的同页先入库，退款号稍后加载时同步升级证据的命名空间；之后收到同笔通知仍可关联。已有可靠身份发生命名空间冲突时报告冲突，不覆盖原记录。继续保留人工修改、确认结果与删除标记。
- **金额角色**：增加本人领取、本次／实际退款、实际到账、红包总额、今日／累计收款等角色，支持小行结构中的金额先到、标签后到，以及金额与“元”拆节点。多个未解释金额不猜测。
- **完成与方向**：区分红包发送、本人领取、他人领取、退还；“交易成功”只证明完成。支付宝／微信品牌中的“支付”二字不作为中性交易的支出依据。红包抵扣仍属于商户支付，不误分成社交红包。
- **自由文本隔离**：已知备注、留言标签的单行值或下一行值不作为成功状态、金额、时间和交易身份依据。失败、待处理、聊天、输入框、密码及页面完整性检查继续保留。
- **近期详情**：仅微信、支付宝的明确凭证标题，有完成状态、可靠交易身份及过去 30 分钟内的交易／到账时间，才允许补采；退款不能用原支付时间替代退款到账时间。其他历史详情继续跳过。金额符号与独立收支类型冲突时拒绝。
- **通知依据**：通知也保存场景、规则版本、方向、状态、金额、退款号与原单号依据，页面和通知共用场景分类及原子写入。
- **诊断**：移除只描述转账付款四锚点的通用失败文案，补充“尚未取得本次红包完成凭证”的原因与补漏说明。常规诊断仍只输出状态和计数。

## 红包自动截图边界

仅扩展已识别的微信支付结果与红包详情入口，不对聊天窗口或任意空页面 OCR。用户必须分别启用页面读取与本地截图补充；系统截图失败、节点含输入／密码、不完整树、窗口切换、授权撤销或旧帧失效时不写入。

发送详情没有交易时间，“准备过红包”不能证明刚付过钱。因此需要先取得本次付款成功事实，再把详情作为同笔证据。取消准备后打开旧红包不能生成支出。领取也不能仅根据进入 `ReceiveUI` 推定成功，必须观察到用户打开红包并读取到本人已存入零钱的结果。未观察到这些信号时保守停止，保留主动图片与账单导入补漏。

准备、完成和详情共用有界流程身份；同笔多个窗口只写一次，新一轮同额红包使用新的流程身份。无明确交易时间的红包记录采用观察时间，不伪造真实付款时分。该机制没有替用户发红包或领取红包，服务的手势执行能力仍为关闭。

## 待设备核验

1. 微信红包付款结果与领取结果的实际 OCR 行、字体和位置，以及系统是否提供“开”的点击文字。发送详情样本不能替代这些验收。
2. 微信／支付宝真实通知标题、通知字段、不同收款码模式、息屏到账、后台自动扣款及多账户环境。
3. 支付宝不同版本的实际节点、H5／自绘页面及截图保护。未在未知支付宝空节点 Activity 上启用通用截图，不能将节点规则通过当成空节点页面已经适配。
4. 真实退款的完整／部分／分次场景及退款身份展示差异；字段缺失、只显示原订单号或只显示退款申请时间时需核对与补录。
5. 其他微信版本、大字、横屏、深色、双开和长时后台。截图和合成节点测试都不等于这些组合已通过。
